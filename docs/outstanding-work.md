## EMF+ rotated high-quality DrawImage

A rotated or sheared `HighQualityBicubic`/`HighQualityBilinear` `DrawImage` (a 3-point destination) is two native draws (round 3; probes `HighQualityRotatedProbe.cs`, `HighQualityRotatedFineProbe.cs`, `HighQualityHalfShiftProbe.cs`, `HighQualityAxisProbe.cs`, `HighQualityAxisNoiseProbe.cs`; modes `hq-rotated`, `hq-axis`, `hq-half-shift`; captures `hq-rotated`, `hq-rotated-fine`, `hq-axis`, `hq-axis-noise`, `hq-half-shift`; code `resampleRotatedTwoStage`, `resampleHqAxisAligned`). The two-impulse probe the task asked for separated the footprints at once: the response is not an area-integrated kernel over the rotated pixel, and not separable filtering along the source axes either; it is the source resampled to a whole-pixel intermediate and then rotated.

- **Rotated None draw = pre-scale + plain-kernel draw, byte for byte.** Drawing the source axis-aligned into a `W x H` bitmap with the same high-quality mode, then that bitmap rotated to the same three points with plain Bicubic (for HighQualityBicubic) or Bilinear, equals the one-step draw exactly in 115 of 120 bicubic and 85 of 120 bilinear captures (`twoDiff3`; the others differ by 1 to 24 bytes of 36,864). `W` and `H` are each edge's device length rounded up (`ceil(length * (1 - 1.5e-7))`: 12.0000029 rounds up, 12.000001, 24.0000019 and 40.0000038 do not, so the length is a float32 result); an edge within one pixel of the source length makes the draw skip the pre-scale and sample the source with the plain kernel (the old "unscaled axis" rule is this case; no intermediate size reproduces it). The old far-edge fade table and the half-pixel shift were artefacts of the missing pre-scale: the intermediate's edge fades through the second kernel's transparent taps.
- **The second pass is plain Bicubic with the axis-aligned integer arithmetic** (premultiplied bytes, 16.16 row stepper, 1/64 phase, weights in 16.16, truncating) on the 8-bit premultiplied intermediate; plain Bilinear is float-like with premultiplied bytes rounded (its interior is a level off on a rare pixel and the exact arithmetic is open). Applied to a directly requested rotated Bicubic it improves the independent captures' counts but regresses a few sums at scales below 1, so it is limited to this second pass.
- **Coverage** is the destination parallelogram scan-converted from its 28.4 corners by the aliased fill rule (as NearestNeighbor), on a transparent border two pixels wide; exactly-on-edge pixels at 45 degrees are excluded as native does.
- **PixelOffsetMode Half/HighQuality:** the same draw with the second pass's grid moved by -0.5 device pixels and by +0.5 *intermediate* texels along each of its own axes (not 0.5 device pixels: it matters when the length is not whole, as at 1.1x), and coverage tested at pixel centres. `hq-half-shift.json` (a search over destination translations of the None draw with the source rectangle moved by -0.5) finds the Half draw exactly, byte for byte, for axis-aligned draws and for unscaled rotated draws (destination moved by -0.5), but never for a scaled rotated one (the best translation leaves 1,674 to 20,326 summed levels over 32 draws), which is why the second pass carries the extra half-intermediate-texel term.
- **Almost axis-aligned quads** (far corners within 0.02 pixels over a 48-pixel edge, ratio about 4.2e-4; 0.03 pixels is rotated; 124 captures, whatever the origin's fraction) draw as axis-aligned ones.
- **Axis-aligned high-quality kernels (stage one) follow fixed-point phases:** step `S = round(65536 / scale)` per destination pixel, position `P = k S + offset` from the first covered pixel (offset `d S` along x, mirrored, `(1 - d) S` along y), weights from the phase `floor((P - 1) / 512)` (1/128 texel) evaluated at the bin centre for the cubic and at the bin top for the tent, the horizontal pass first and rounded to 8 bits before the vertical one. This took the axis-aligned arithmetic captures from 6 of 288 exact to 206 and the independent ones from 8 to 38 of 192 (`hq-arithmetic-bounds.json` tightened on 869 metrics). The tent is exact on 46,569 noise values; the cubic differs by one level on 35 (0.08%).

### Round 4: measured cubic weights, reductions, mirrors, wraps and the corner snap

Probes `HighQualityCubicWeightProbe.cs` (mode `hq-cubic-weights`, source rows from `generate-hq-cubic-source.ts`), `HighQualityPhaseProbe.cs` (`hq-phases`), `HighQualityReductionProbe.cs` (`hq-reductions`, scratch analysis only, not committed: 11 MB) and `HighQualityWrapProbe.cs` (`hq-wrap`); captures `hq-cubic-weights`, `hq-phases`, `hq-wrap`; code `src/emf-plus-hq-cubic-weights.ts`, `resampleHqAxisAligned`, `hqReductionTaps`, `snapOriginKeepCorners`; tests `emf-plus-hq-cubic-weights.fixture.test.ts`, `emf-plus-hq-phases.fixture.test.ts`, `emf-plus-hq-wrap.fixture.test.ts`.

Rules found, with the evidence:
- **The cubic weights are a measured integer table.** Rows of designed noise (400 rows, 1,016 texels, drawn 128/127 wider so every destination column visits all 128 phase bins; about 2% of the sums fall within 0.02 of a half level, chosen offline) leave exactly one integer weight vector per bin that reproduces all 1,221,600 native values; the table is exactly symmetric (bin `127 - b` is bin `b` reversed) and sums to 65536 in every row. 88 of the 128 rows equal the kernel integral with each texel edge rounded to 1/65536 (426 of the 1.2 million values differ for that analytic table); the other 40 differ by one unit between two adjacent taps. The deviations are ±0.1 to 0.2 of a unit at the texel edges, larger than a float32 evaluation of the cumulative polynomial gives, and no numerical-integration, bit-depth or kernel-parameter variant reproduces them, so the 64 rows (the other 64 mirror them) ship as data (`HQ_CUBIC_HALF_TABLE`, 640 integers). Result: axis-aligned bicubic noise upscales 35 of 46,569 values off to 0; arithmetic captures 206 to 288 of 288 exact; independent captures 38 to 122 of 192; rotated bicubic upscales and Half draws improve with the same table (Half noise: 0 exact of 20 to 17).
- **Reductions use the same machinery in destination space.** Each source texel edge `e` (relative to the source origin) lands at `s (e - P)` destination pixels, `P = (k S + offset) / 65536`; that offset is rounded down to 1/128 pixel and a texel's weight is the difference of the kernel's running integral at its two edges' offsets: the cubic's half-grid table above (`T(m)` at `(m + 1/2) / 128`, rebuilt from the measured weights), the tent's `512 j - 2 j^2` at whole grid points. - **Clamp to a transparent colour is no WrapMode.** All 28 native Clamp-transparent draws equal the draw without attributes pixel for pixel, in every shape. The other modes change only a ring about two pixels wide inside the quad (24,523 pixels over 140 draws). Axis-aligned draws read the wrapped (or clamp-coloured) texels through the same weights and are exact at 1.55x, 2.25x and 0.625x in every mode (over 2,000 pixels per mode off before); a rotated draw is the two-stage draw with the wrap on the source in the pre-scale and on the intermediate in the plain pass (about 1,085 pixels more than 3 levels off over four 25-degree draws down to 230).

- Real fixtures (zero tolerance, 15,741 pixels each): `gpx-image-highqualitybicubic` 1,084 to 121 pixels off, `gpx-image-highqualitybilinear` 1,145 to 34, `gpx-image-pom-half-highqualitybicubic` 294 to 28, the three WrapMode HighQualityBicubic fixtures 3,417 to 3,641 down to 77 to 120; every one is now within one level at tolerance 1 (`gdi-parity.fixture.test.ts` tightened from eight levels). Bundle: `dist/index.mjs` 1,915,916 to 1,922,296 bytes.

## EMF+ gradients

Path gradients with uniform surrounds are closed to the step and, but for some of the pixels exactly on a copy's edge, to the pixel; ones with per-vertex surround colours are Gouraud fan triangles. GDI+ draws a path gradient as `N = ceil(2 * hypot(w, h))` nested copies of its boundary (`w` x `h` is the device-space bounding box: a 600 x 80 rectangle has 1,211 steps, 2,422 under a world or brush scale 2, and a diagonal that is a whole number of quarter pixels is not rounded past itself), each a step closer to the centre colour, and a pixel takes the colour of the innermost copy that holds it. `pathGradientQuantum` and `quantisedPathArgb` (`emf-plus-brush-gradient.ts`) rebuild that: the ratio rounds to a whole step, the outer half counts steps from the boundary colour and the inner half from the centre colour (they round a level apart at half-way), premultiplied channels and alpha interpolate together, and Blend and InterpolationColors curves are read at the stepped position. The sampler in `emf-plus-exact-fill.ts` passes the step count; the nudge that selects a left-inclusive span no longer moves the sampled ratio.

How it was found: the probe in `PathGradientStepProbe.cs` captures whole rows through white-to-black rectangles, where the path-gradient geometry is trivial (a row is the plane `255 x / half-width` up to rounding). 97% of values matched round(255 t); the remainder looked like noise until it was seen to depend on the rectangle's HEIGHT (rows of identical width and different height fall into groups whose boundaries sit where `floor(4 * L)` changes, `L` the half diagonal). Left and right of the centre mirror exactly; the left half is `round(255 k / N)` and the right half `255 - round(255 k / N)` for the step count `k = round(t N)`. The step count follows the half diagonal of the bounding box for rectangles of every size and centre, for triangles and ellipses (centred or not), under world/brush scales (device-space bounds), with Blend and preset curves read at `k / N`, and for isotropic focus (contours scaled about the centre). 72 rows reach 25,390 of 25,568 pixels; the 64 images 99.25-100%; the earlier 120 colour, 240 alpha, 252 focus-contour captures rise by 98,306, 20,132 (translucent), 35,628 (uniform alpha) and 18,270 exact pixels (see limitations.md for the totals), with every per-capture ceiling in `path-gradient-color-bounds.json` tightened (176 of 360 entries) and none loosened.

Per-vertex surround colours are not nested copies at all. GDI+ fans the boundary into triangles (centre, vertex i, vertex i + 1) and Gouraud-shades each with a whole-pixel scan converter; `emf-plus-path-gradient-vertices.ts` reproduces it. Found by isolating one channel at a time (a red-only vertex makes each channel the weight map of one vertex; the three channels of an RGB triangle are independent and identical to the three single-channel captures) and then reading how the colour behaves along one scanline of one fan triangle:
(1) a span runs from `ceil(xLeft)` to `ceil(xRight)` at the integer row, with no sub-pixel correction, so the colour at the first pixel is the left edge's colour rather than the colour at the crossing (this alone is the x shift of about -0.5 pixel that a plane fit to the colour shows, and it is why a smooth fan model is up to four levels off on slanted edges but not on a horizontal one); the right edge's colour belongs to `ceil(xRight)`, the first pixel past the span, so the per-pixel step is the end difference over `xe - xs`, not over the true width. (2) Each edge is walked along its major axis (x when |dx| > |dy|) in `trunc(|d|)` whole steps from `floor` of its first vertex, taking the edges in the order centre -> vertex i, vertex i -> vertex i + 1, vertex i + 1 -> centre; the edge parameter at a column or row `u` is `|u - floor(a)| / trunc(|b - a|)` (the colour at `x = 32` on one edge was `k / 11` for six rows, with the denominator `trunc(11.69)`; rows give `k / 13` for a 13.75-row edge). (3) The span interpolates in 16.16 fixed point with the step taken by `floor` (a toward-minus-infinity shift), the ends truncated, and the pixel rounded half up: a tie such as a constant 127.5 row rounds up while a drifting row loses a fraction to the floored step, which is why ties looked like they round toward the centre colour in an earlier fit. (4) Alpha and the premultiplied channels interpolate together (translucent captures: 2,180 of 2,181 exact against 2 of 2,181 for straight-alpha interpolation). (5) Device vertices reach the scan converter rounded UP to 1/16 pixel (`ceil(16 v) / 16`; rounding to nearest, truncation and floor all lose 10-20 points of exactness on scaled and rotated captures; quarter turns, 0.75 and 0.6 scales and 10, 25, 30 and 90 degree rotations are the evidence). (6) FocusScales do nothing when the surrounds differ per vertex: 40 captures with isotropic (0.5, 0.5) and anisotropic (0.25, 0.75) scales are 98.7% exact (14,577 of 14,766, none beyond a level) from the plain fan, against 0.5% for the previous model, and the differing-pixel ceilings of the 240 alpha controls (80 of them with a focus) fall from 255,177 to 33,604 in total. Measured on 320 captures (`path-gradient-vertices.json.gz`, `src/emf-plus-path-gradient-vertices.fixture.test.ts`): 120 random polygons on a 1/16 grid 98.78% exact (44,454 pixels, none beyond one level; 0.83% before), 60 translucent ones 99.31% (0.08% before), the four RGB triangles (black and white centres, scales 4 and 0.5) 99.7% (29% before), eight triangle orientations 94.2% (22% before), the single-channel set 98.9% (52% before), quad 97.3% and pentagon 97.7% (11% and 21% before), scaled and rotated sets 95.8-99.0% (0.2-1.0% before); every pixel of these is within one level. `grad-path-triangle-clamp` falls from 1,421 to 13 differing pixels at zero tolerance (none beyond a level), the tiled triangles from about 6,000 (38%) to 70-72 (0.45%); All 120 per-vertex captures of the 240 alpha controls tighten.

Rotated, sheared and anisotropically scaled uniform path gradients take their step count from the UNtransformed bounds: `N = ceil(|M(w, h)| + |M(w, -h)|)` for the brush-space bounds `w` x `h` and the linear part `M` of the brush-to-device matrix (the sum of the two device diagonals of the bounds; it is `ceil(2 * hypot(w, h))` for an unrotated scale, and a rotation does not change it). `PathGradientRotateProbe.cs` captured 70 gradients (a rectangle, a triangle and a wide rectangle, centre off the middle, fractional translation) as world and as brush transforms (the two give identical pixels): rotations of 0 to 200 degrees, a 1.5 x 0.7 scale, a 30-degree rotation of a 2 x 1 scale, shears of 0.25 to 2 in either axis and mixed matrices. Scoring every step count from 60 to 700 against each capture put the best count at the formula's in all 70 (no other count within 12 of it scored as well); the device bounding box of the rotated shape (which grows with the angle, 194 against 145 for a 60 x 40 rectangle at 30 degrees) scored 61% over the first 48 captures, the untransformed bounds 74%, the column norms of `M` 84% (right for rotation and scale, 3 to 6 steps too many under shear), and the diagonal sum 90%. The rest of the 10% was the rounding of the copies, next paragraph (fractional geometry puts a pixel within a few hundredths of a step of a copy edge often: an unrotated rectangle scored 95%). The step count was the only thing wrong with rotation: the nested copies are scaled about the centre in brush space and transformed, which the sampler already did.

Which copy holds a pixel is decided by the geometry GDI+ actually scan-converts, and that closed the ties and near-ties the ratio model rounded the wrong way (`emf-plus-path-gradient-copies.ts`, `pathGradientStepColor`). (1) The boundary's vertices and the centre are rounded to the nearest 1/16 pixel in device space (28.4 fixed point) before anything is scaled; copy `m` is then the exact scale of those points about the rounded centre by `(m + 1/2) / N`, with no rounding of its own, and a pixel takes the innermost copy holding it (an isotropic focus `f` scales a copy by `f + (1 - f)(m + 1/2)/N`, independent focus scales do it per axis). Scoring four fractional-geometry captures (a rectangle and a triangle, each at two rotations, 7,423 pixels): rounding the points to nearest and scaling exactly 100.00%; rounding nothing 91.1%; rounding the copies as well to 1/16 82%, to 1/256 91%; rounding the original points up 81% or down 77%. Over the 46 world-transform captures of the rotated set (107,809 pixels) the exact-scale model is 100.00%, where the smooth ratio with the right step count scores about 90%. (2) A step's colour rounds a value exactly half way between two levels toward the centre colour: 59% of the pixels of an opaque capture with a small colour range (alpha control 236: red 173 to 155, green 43 to 125, blue 6 to 123 over 164 steps) were on the ramp with half-up rounding and 99.93% with the tie rule; 186 of the 240 alpha controls and 20 of the 120 colour controls tighten, and the sum of the 240 alpha differing-pixel ceilings falls from 255,177 to 1,389, and a wider tie margin (1e-4 to 1e-2 of a level) scores worse, so the 0.01-0.02 margin the step-count round measured was the geometry's near-ties. (3) Independent focus scales are the same copies scaled per axis: ten scale pairs on a rectangle (100% of 100,000 pixels in step-reading captures, 99.93% by colour: the rest are one-level ties of a fully focused axis), on a diamond (98.9%) and on a triangle (99.6%), and 40 random triangles and quads (99.2%); the focus-contour captures' anisotropic exact pixels rise from 1,594,271 to 1,725,250 of 1,728,000 with every per-capture ceiling held or lowered, `grad-path-focus-*` rectangles with scales 75/25, 25/75, 50/0 and 0/50 are pixel-exact, `grad-path-ellipse-clamp` falls from 14 differing pixels to none and `gpx-pen-pathgrad` from 48 to 2.

Hypotheses rejected, with evidence: (1) a function of the ratio alone quantised to a fixed number of steps, or to any 2^k, in any rounding (rows of equal width and different height differ); (2) a fixed-point linear ramp with a rounded slope and offset per row (no linear fit exists for either half); (3) the linear-gradient knot table with 8- or 16-bit interpolation (best 259 misses of 8,677 values against 259 for plain rounding); (4) the vertex-distance quantisation as a scale `L / Lq` on the ratio (no better than plain rounding); (5) a 16- to 24-bit fixed-point weight or reciprocal for the sub-level residual below (best 405 misses of 138,188 left-half values against 637 for exact arithmetic); (6) float32 barycentric or edge-DDA arithmetic, edge left/right inclusion and a dx-sign rule for the exact half-step ties (each fits some of the 493 tie pixels and none all: the same geometry in the opposite vertex order flips about half of them); (7) whole-triangle Gouraud or fan-apex Gouraud models for per-vertex surrounds as exact barycentric fills (50% of pixels and errors up to four levels): the fan model was right, the missing piece was the scan converter (see above). (8) rounding the copies to 1/16 or a finer grid, or rounding the original points up or down, and float32 evaluation of the copy scale or of the vertex arithmetic in any of ten orders (see above; none changes the integer-sized ties); (9) a wider tie margin for the colour rounding; (10) a step count from the device bounding box of a rotated shape, from the untransformed bounds, from the column norms of the matrix or from its determinant (61%, 74%, 84% and 75% against 90% for the diagonal sum on the rotated captures, before the copies model took the set to 100%).

Pixels on a copy's edge are float32 (`emf-plus-path-gradient-copies.ts`, `floatCopyIndex`; found after the binary-fraction rule below, which it supersedes for every uniform path gradient without a focus). The single-edge, slope and corner captures put 76,000 pixels exactly on a copy's edge in front of the arithmetic, and the rule that fits all of them is: with `a` the first vertex of the fan triangle's boundary edge relative to the centre, `e` the edge vector and `d` the pixel relative to the centre (all in 1/16 pixel multiples, exact in float32), `u = (ay dx - ax dy) / (ex dy - ey dx)`, `b = a + u e` componentwise (the product `u e` rounded, then the sum), the pixel's larger coordinate of `b` (by magnitude, the x coordinate when equal) picks the component, `r = |d_c / b_c|`, and the copy is `floor(N r + 1/2)`, where every operation (the products and difference of the numerator and denominator of `u`, the division for `u`, the product `u e`, the sum, the quotient, the product with `N`, the sum with 1/2) is a float32 operation rounded toward minus infinity. The captures cannot say whether native rounds the products and differences of `u`: computing them exactly, or rounding the difference only, gives the same copy for every pixel of every committed capture, including twelve shapes of 300 to 700 pixels at fractional vertices (`PathGradientLargeProbe.cs`, 984,120 pixels, where the products do need more than 24 bits). A step colour is the open part of those large captures: 24 of 13,657 steps seen (N between 954 and 1,278) are rounded up by native when `255 k / N` is 0.0005 to 0.009 below a half level, which moves 2,534 pixels (0.26%) and the 42 pixels of `tri-base` (N = 367, red at step 57, 56.4986) one level; the shift grows with the number of steps from the centre colour (about 6e-6 levels per step), the signature of a step that is slightly short, and no position quantisation (8 to 24 bits), no float32 chain and no fixed-point step of 8 to 24 bits reproduces all of them (a fixed-point step accumulated from the centre at 18 bits gets 12 wrong, 16 and 17 bits more). How it was found: the clean data was a fan triangle with the centre ON a vertex (`PathGradientCornerProbe.cs`: a single linear colour function, one edge in play, 1,720 captures) and sheared rectangles (`PathGradientSlopeProbe.cs`, 684), whose slanted ties were 82 to 86% explained by the binary-fraction rule and 76% by ray-and-edge fixed-point models. A search over rounding modes applied to every operation of the ray-and-edge computation (toward zero, to nearest, down, up; 64 combinations of per-stage choices in fixed point had topped out at 85 to 97%) put "all float32, all rounded down" at 99.76% of the corner ties and 97% of the rectangle ones in one step; the last 3% were the diagonal pixels (|dx| = |dy|) of a vertical or horizontal edge, which the rule 'the larger coordinate of the boundary point' (not of the pixel) resolves, and the result is 100% of 27,748 labelled non-natural ties in four independent sets and every pixel of 404,004. Rounding down is why the ratio of a pixel on a left or top edge differs from its mirror on a right or bottom edge (negative values round away from zero) and why the binary-fraction rule held for the exact-coordinate pixels (the quotient of two small integers is exact exactly when it is a binary fraction, else it falls short). ### Grayscale hinting and scan conversion (round 5, V1, 8 October 2026)

**Probes and data.** `RealGlyphCoverageProbe.cs` (`text-real-glyphs`): every printable ASCII glyph of 14 face/style combinations at 9 to 24 ppem, AntiAlias and AntiAliasGridFit, 31,584 captures. `build-raster-fonts.py` with `RasterPolygonProbe.cs` and `RasterMonoProbe.cs` (`text-raster-polygons`, `text-raster-bars`, `text-raster-mono`, `text-raster-variants`): program-free private fonts of 256 polygons on the 1/64-pixel lattice (plus 272 thin bars, `-stN` variants running `SCANCTRL 0x1ff` and `SCANTYPE N`, and variants adding a stack declaration, a glyph program, a `cvt` table or an empty `prep`) captured through GDI+ `DrawDriverString`, GDI `GGO_BITMAP` and `GGO_GRAY4_BITMAP`. They isolate scan conversion because nothing is grid-fitted.

**Rules found.**

- *Instruction budget (a bug, fixed):* the 1,000,000-instruction guard counted over the life of a size, so after about a million instructions every later glyph of that size aborted at its first instruction (`src/ttf-hinting-budget.test.ts`). The fix moves `textx-plus-singlebit` from 394 to 392 differing pixels (bound tightened to 1.941%) and `textx-couriernew-aa` from 186 to 190, the second from a glyph the old accident happened to match.
- *Default dropout control (shipped, monochrome):* a font that never runs `SCANCTRL` is scan-converted with simple dropouts (mode 0) up to 32 ppem and none above. Evidence: GDI monochrome bitmaps of the program-free font, 4,079 of 4,096 at 8 to 32 ppem and 1,024 of 1,024 at 33 to 40; the four hinting-machinery variants give 1,787 of 1,792 and 512 of 512 each (`src/ttf-gray-dropout.fixture.test.ts`). - *Grayscale dropout control (shipped for SCANTYPE 0 and 4):* AntiAlias images are GDI's `GGO_GRAY4_BITMAP` bitmaps with the 17th level mapped to the 16th (4,969 of 5,120 images equal, the other 151 pixels one sample lighter in GDI+), and the bitmaps apply the font's scan control to the oversampled outline. ## Tooling

- **Regenerating existing groups:** running existing fixture groups on the Windows runner can change their PNGs, because the runner's OS, fonts and DPI can differ. Compare before replacing committed fixtures.

Every new generator run writes an `environment-<groups>.json` manifest associating reference hashes with Windows/native-library versions, screen DPI and installed font hashes. This makes subsequent environment changes detectable; it cannot recover the environment of earlier captures.
